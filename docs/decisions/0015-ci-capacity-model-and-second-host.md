# 15. CI capacity model: multi-gate admission, measured reserves, and a generated report

Date: 2026-08-08

## Status

Accepted.

## Context

`personal/ci-controller.yml` went through **8 config versions in 47 days**. Each
revision was carefully reasoned from the data available at the time, and each
reached a conclusion that disagreed with the last. That churn was not operator
indecision — it was a symptom of a broken instrument:

- **`evaluate()` recorded only the first binding gate.** `admission.py` checked
  `lane_ceiling` before `budget_full` and returned on the first match. Whenever
  lanes were full, every deferred job was stamped `lane_ceiling`, even on the
  jobs the RAM budget would also have rejected. `budget_full` was only ever
  observable *below* the lane ceiling — so a tuning round that read "lane_ceiling
  dominates, add lanes" could not tell whether budget was the real constraint,
  because the data structurally couldn't say so.
- **What was learned lived only in YAML comments**, rewritten (and partly
  overwritten) on every pass. There was no durable record connecting a config
  change to the observation that justified it, so nothing stopped the next round
  from re-deriving — and re-disagreeing with — a conclusion two versions back.
- **A stale RAM figure produced a wrong conclusion once already.** `peak_ram_mb`
  recorded before 2026-07-30 counted reclaimable page cache, not the process's
  actual working set. A tuning round that quoted a pre-fix percentile as if it
  were a real ceiling was reasoning from a number that measured the wrong thing.
- **A drain-the-backlog config choice produced a real outage.** On 2026-08-07,
  running the controller at 7 concurrent lanes while draining a backlog drove a
  15-minute load average of 191, starved `sshd`, and OOM-killed four processes;
  the box was unreachable for roughly 35 minutes. The reserve values in place
  before that incident were not wrong in isolation — they were being pushed
  toward the observed median usage rather than held against the observed peak.

None of this was a single bad decision. It was an instrument that couldn't
distinguish the hypotheses under test, feeding a config format with no memory.

## Decision

1. **Admission records every binding gate, not just the first.** `evaluate()`
   now returns all gates a deferred job failed — lane ceiling, budget, disk,
   KVM, host pressure — as `DeferDecision.reasons: tuple[str, ...]`, with
   `.reason` (its first element) preserved for continuity with the ~112,000 rows
   already recorded under the old, single-reason schema. Any report built on top
   of this must present both the primary-reason view (comparable to history) and
   the binding-gate view (the masking-corrected one), and say plainly when the
   corrected view isn't available yet rather than silently substituting the
   primary-reason count for it.

2. **Reserves track the measured p90 of actual peak usage, and are never
   lowered toward the median.** The 2026-08-07 incident is why: p50 is what a
   class usually needs, not what it needs at its worst, and a reserve sized to
   the median admits combinations of jobs whose simultaneous peaks the box
   cannot survive. A capacity gate may be raised toward p90 (or higher, e.g. p95
   for a class with a costly failure mode) on new evidence; it is not lowered
   toward p50 on the argument that most jobs don't need that much.

3. **A class's bimodal RAM footprint is a class-granularity defect, not a
   reserve-value defect.** The `node` class shows p50 ≈ 1.27 GB and p90 ≈ 5.9 GB
   (post page-cache-fix data) — two populations of jobs sharing one label. The
   correct response to bimodality is to split the class once the underlying
   cause is identified (Task 3 captured `workflow` and `job_name` on every
   queued job for exactly this purpose — the GitHub payload always carried them
   and the adapter had been discarding them), not to average the two peaks into
   a single reserve that is simultaneously too small for the heavy half and
   wasteful for the light half.

4. **Capacity numbers are generated by `ci-bench`, and a change to a
   `ci-controller.yml` capacity gate must cite a section of the generated
   report.** `services/ci-controller/src/ci_bench.py` computes admission-gate
   counts (primary and binding-gate), per-class peak-RAM percentiles, queue
   wait, and infra-failure rates directly from the `events` table, and
   `make ci-report` regenerates `docs/ci-capacity-report.md` from the live
   host's database. `personal/ci-controller.yml`'s inline comments now point at
   report sections instead of restating derived numbers, so the numbers cannot
   drift out of sync with the data that produced them. This is the mechanism
   meant to end the 8-versions-in-47-days pattern: a reasoned-but-uncited config
   change is exactly the failure mode being closed off. A change without a
   citable report section should be treated as unreviewable, the same way a
   code change without a passing test would be.

5. **Additional capacity comes from a second host under one controller and one
   ledger, never a second controller.** Two independent controllers each
   admitting against their own local budget can't see each other's load, so
   nothing stops both from admitting a burst simultaneously and the combined
   result exceeding what either host alone was tuned for. A single controller
   with a per-host ledger keeps admission decisions globally consistent and
   keeps `ci-bench` a single join over one `events` table instead of a
   reconciliation problem across two.

6. **On an operator-shared machine, CPU is rationed by priority, RAM by a
   floor.** `powerserver` and any second host also run the operator's other
   homelab services. CPU contention degrades gracefully (a CI job runs slower);
   RAM exhaustion does not (the kernel OOM-kills something, possibly not the CI
   job). The capacity model therefore treats RAM as the hard admission gate and
   CPU as a soft, lower-priority one — consistent with ADR 0012's finding that
   CPU, not RAM, was the binding constraint on `powerserver`'s original
   hardware, but for a different reason: RAM failure modes are destructive,
   CPU's are merely slow.

## Consequences

- **The report must be regenerated after any capacity-relevant config change.**
  `docs/ci-capacity-report.md` reflects the `config_version` active when it was
  generated; a stale report cited to justify a new change is citing evidence
  for a different configuration.
- **Pre-2026-07-30 peak-RAM data stays permanently unusable.** `ci_bench.py`
  hard-excludes reap events before that timestamp
  (`PAGE_CACHE_FIX_TS`) from peak-RAM percentiles; this is not a filter that
  should be relaxed as the affected data ages out, because the values
  themselves are wrong, not merely old.
- **`infra_failures` has a derived validity floor, for the same reason
  `peak_ram_mb` has `PAGE_CACHE_FIX_TS`.** The `conclusion` column did not
  exist for ~112,000 historical rows, so their `conclusion IS NULL` means
  "the column didn't exist yet," not "the job's outcome was unknown." Unlike
  the page-cache fix there is no fixed calendar cutoff — it depends on when
  the operator deploys — so `ci_bench.py` derives it from the data: the
  earliest reap `ts` with a non-NULL `conclusion` marks when the controller
  started writing the column, and only reaps at or after that point count
  toward `infra_failures`. Without this floor, the first report generated
  after deploy would have misread all ~3,994 historical reap rows as infra
  failures. The controller also now writes `lookup_failed` and `adopted` as
  distinct sentinels instead of leaving `conclusion` NULL for those cases, so
  a NULL conclusion after the floor means only "genuinely no terminal
  outcome" — `lookup_failed` (e.g. a runner App missing `Actions: Read`) is
  reported separately, since it means "unknown," not "failed."
- **The binding-gate (masking-corrected) view has no data yet.** The controller
  that writes `reasons` has not been deployed as of this ADR, and the ~112,000
  historical rows keep `reasons` NULL by design — no backfill was attempted, so
  there is nothing to backfill correctly. The binding-gate columns in the
  generated report read "unavailable" until new traffic accumulates after
  deploy, and any claim about which gate actually dominates must wait for that
  data rather than being read off the primary-reason count, which is exactly
  the number this decision says is unreliable.
- **Primary-reason ranking is itself window-dependent, which is an argument for
  a report that states its window, not evidence of instability.** Over the
  47-day history, `budget_full` (1862) outranks `lane_ceiling` (1230); over the
  most recent 7 days, `lane_ceiling` led. Both are real; they describe
  different periods of a system whose load and config both changed underneath
  them. A citation to "the report" is only meaningful if the report states the
  window it covers, which `ci_bench.py`'s output does.
- **A second host is opportunistic capacity, not a dependency.** Whatever host
  is added must be skippable — a failed health check on it defers to the
  existing host rather than failing the job — so CI degrades to today's
  behavior rather than to a new single point of failure.
- **This ADR does not itself prove the second host is warranted.** Phase 3's
  design (a `hosts:` config shape) is informed by whether `lane_ceiling`
  survives the binding-gate correction as the dominant gate once real data
  exists — the premise for adding lanes/hosts at all. That data does not exist
  yet; writing the phase now would be tuning ahead of the instrument again.
